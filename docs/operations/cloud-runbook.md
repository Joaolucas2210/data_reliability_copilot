# Cloud runbook (Terraform)

Scope: Azure reference path + AWS/GCP foundations under `infra/terraform/`. **Nothing in this runbook has
been executed against a real account yet** (2026-10-09); the steps are the intended procedure and must be
dry-run with `plan` before the first apply. Applies are manual and operator-run in this phase. CI only runs
static checks, plus `plan` on manual dispatch.

## 0. Prerequisites

- Terraform 1.16.5 (or `infra/terraform/check.sh`, which runs it in Docker).
- An operator identity with rights to create the state resources (Owner on the subscription / admin on the
  account / `roles/owner` on the project): used **only** for bootstrap.
- Never put secrets in `*.tfvars`. Copy `terraform.tfvars.example` → `terraform.tfvars` (gitignored).

## 1. Bootstrap order (once per cloud)

| Step | Azure | AWS | GCP |
|---|---|---|---|
| 1 | `cd azure/bootstrap && terraform init && terraform apply` | `cd aws/bootstrap && …` | `cd gcp/bootstrap && …` |
| 2 | Write outputs into `envs/dev/backend.hcl` (`resource_group_name`, `storage_account_name`) | Pass `bucket=` as `-backend-config` | Pass `bucket=` as `-backend-config` |
| 3 | Record `ci_client_id` as GitHub env var `AZURE_CLIENT_ID` (with `AZURE_TENANT_ID`, `AZURE_SUBSCRIPTION_ID`) | Apply `aws/foundation` and record `AWS_CI_ROLE_ARN` | Apply `gcp/foundation` and record `GCP_WIF_PROVIDER`, `GCP_CI_SERVICE_ACCOUNT` |
| 4 | Grant the CI identity roles on the env RG (Reader for plan, Contributor + User Access Administrator scoped to the RG for apply) |: (policy is in the foundation) | Grant the plan/apply roles on the project |

Bootstrap state is **local** by design. After step 1, either keep `terraform.tfstate` in a restricted operator
vault or migrate it into the bucket/container it created (`terraform init -migrate-state` after adding a
backend block). The state stores are protected from deletion (Azure management lock, AWS/GCP `prevent_destroy`).

## 2. State and locking

- Azure: blob lease per state key (`azure/<env>/<component>.tfstate`); Entra ID auth only (`use_azuread_auth`, shared keys disabled).
- AWS: S3 native lockfile (`use_lockfile = true`, Terraform ≥ 1.10); versioned bucket.
- GCP: GCS native locking; versioned bucket.
- Stuck lock: confirm no run is active (CI run list), then `terraform force-unlock <LOCK_ID>`. Never delete
  lock objects by hand while a run might be in progress.
- State rollback: restore a previous object version (all three buckets are versioned), then `terraform plan`
  to see the drift before doing anything else.

## 3. Secrets

Terraform creates **secret containers/names only**:
`pg-app-password, pg-dbt-prod-password, pg-reader-password, pg-sandbox-password, llm-api-key`.
Set the values out-of-band:

```bash
az keyvault secret set --vault-name <kv> --name pg-app-password --value "$(openssl rand -base64 32)"
aws secretsmanager put-secret-value --secret-id drc-dev/pg-app-password --secret-string "$(openssl rand -base64 32)"
printf %s "$(openssl rand -base64 32)" | gcloud secrets versions add drc-dev-pg-app-password --data-file=-
```

The Postgres **admin** password on Azure is generated by `random_password`, so it **is in state**. State is
therefore sensitive: access is restricted to the CI identity and operators. Gap: switch to Entra-only admin.

## 4. Deploy order and migrations (Azure)

1. CI builds and pushes `drc:<git-sha>` (gap AZ-6).
2. `terraform apply` with `image_tag=<git-sha>` **does not** shift traffic before migrations, because the next step is gated:
3. Run migrations first: `az containerapp job start -g <rg> -n <migrate_job_name>`, then wait for `Succeeded`
   (`az containerapp job execution list`).
4. Only then roll the app revision (`revision_mode = Single`).

Migrations are forward-only and must stay **backward compatible with the previous app version**
(expand → migrate → contract across two releases). The app checks `schema_migrations` at start and refuses
to run against an unknown newer version.

Rollback: redeploy the previous `image_tag`. Never roll back a migration in place: write a new forward
migration. For data damage, use PITR (§5).

## 5. Backups and restore

- Azure Flexible Server: automatic backups, `backup_retention_days` (7 in dev), PITR to a **new** server:
  `az postgres flexible-server restore -g <rg> --name <new> --source-server <old> --restore-time <UTC>`.
  Geo-redundant backup is OFF (single-region RPO), and enabling it later requires a new server.
- After restore: point `DRC_PG_HOST` at the new server (Terraform variable or import), run `drc migrate`
  (no-op expected), and run the smoke checks (`/api/pipelines/health`, the isolation test).
- Restore drills: at least once per quarter in non-prod. Record the duration (RTO) and the restore point gap
  (RPO) in this file.
- Artifacts (Blob): versioning + 14-day soft delete; lifecycle deletes run artifacts after 90 days
  (retention policy, see the architecture doc's retention section).

## 6. Inventory

Every resource carries `app=drc, env=<env>, owner, cost_center, managed_by=terraform` (labels on GCP).

```bash
az resource list --tag app=drc --query "[].{name:name,type:type,rg:resourceGroup}" -o table
aws resourcegroupstaggingapi get-resources --tag-filters Key=app,Values=drc --query 'ResourceTagMappingList[].ResourceARN'
gcloud asset search-all-resources --scope=projects/<project> --query='labels.app=drc' --format='table(name,assetType)'
terraform state list   # per root: what Terraform believes it owns
```

Drift check: `terraform plan -detailed-exitcode` (exit 2 = drift).

## 7. Shutdown (stop spending, keep data)

Azure dev:
```bash
az containerapp update -g <rg> -n ca-drc-dev-<r>-api --min-replicas 0 --max-replicas 0   # or set api_min_replicas=0 (default)
az containerapp update -g <rg> -n ca-drc-dev-<r>-worker --min-replicas 0 --max-replicas 0
az postgres flexible-server stop -g <rg> -n <server>   # Azure auto-starts a stopped server after 7 days
```
Remaining fixed costs while stopped: storage (Postgres disk + backups, Blob), ACR Basic, Key Vault operations,
and Log Analytics retention. AWS/GCP foundations hold only near-zero-cost resources (KMS key monthly fee on
AWS, secret versions, registry storage).

## 8. Destroy

1. Export anything worth keeping (eval results, incident audit trail: `pg_dump app`).
2. `terraform plan -destroy` and review it. Key Vault soft-delete keeps names reserved for
   `soft_delete_retention_days` (7). Purge only if necessary, because purge protection is ON in prd.
3. `terraform destroy` per env root, **in reverse dependency order** (env roots, then foundations; bootstrap last
   and only when the whole project is being retired: remove the management lock / `prevent_destroy` first).
4. Run the inventory queries (§6): they must return nothing except the state store.

## 9. Cost guardrails

- Budgets: alerts at 50 % actual and 90 % forecast on all three. **Alerts do not stop spend.**
- Defaults are chosen to be cheap: Container Apps `min_replicas=0`, worker `max_replicas=1`, Postgres
  burstable B1ms + 32 GB, ACR Basic, Log Analytics `daily_quota_gb=1` and 30-day retention.
- Before any apply: price the plan for the target region with the provider's pricing calculator and record
  it in the PR. No apply has been done, so **there is no measured cloud cost yet.**
- AWS: activate `app` as a cost-allocation tag, otherwise the budget filter matches nothing.
